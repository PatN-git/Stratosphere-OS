## 1
A job found by the nightly scan goes live only if it scores at least 85 out of 100 and none of these apply: its apply link is invalid or known dead, it is a talent-pool or open-application post, it only links to the company's general careers page, its job category is not a recognised one (or the company's categories are unverified), or its location looks foreign. Any other job is a draft, except that a foreign location with no German match is archived instead, unless the link is also broken, in which case it stays a draft. A job already stored as live under the same apply link is not demoted by a re-scan. Live jobs are archived later when they are missing from two scans of their company in a row, or the daily link check finds the page gone (404/410), saying the job is closed, failing twice in a row, or the job was posted over 180 days ago.
## 2
The 10 points are given unless the job is explicitly marked as having a failing apply link. In the ingestion code nothing marks a link as failing, so the link is not actually tested at that moment and the job normally gets the 10. If the apply link is not a valid http/https address, or the title is two characters or fewer, the whole score is 0 and there are no points at all. The total can still be capped afterwards (for example at 80 for a portal-only link and 75 for a talent-pool post), and a link marked failing would also make the job a draft with reason "unreachable link".
## 3
The title counts three times as much as the department: a title match is weighted 1.5 and a department match 0.5, for example 15 versus 5 points for the strongest keyword group. A department keyword only adds points for a group the title did not already match, while a "negative" keyword costs 15 points whether it is found in the title or the department. A category needs at least 4 points to win, otherwise the job is "other", so a department on its own would have to hit the strongest keyword group to clear that bar. Only some feeds pass the department at all (Ashby, Personio, Recruitee, Workable, Join's category, the AI reader and the page scraper); Greenhouse, Deel, HeavenHR, HiBob, TalentStorm and Teamtailor use the title only.
## 4
Each job-board connector takes them from the board's own fields where it has them (for example a workplace-type or employment-type field, and for a few connectors a seniority field) and otherwise reads keywords in the job title, with seniority sorted into six levels. If nothing is found, the job is saved with the defaults experienced, full time and hybrid. For most connectors those defaults earn no score points and count as missing in the draft diagnostics; HeavenHR, Deel and Teamtailor fill in some defaults themselves beforehand, and Recruitee and the page scraper count them when scoring.
## 5
It covers only the Gemini AI reader that read the page: after a quota error (an HTTP 429, or a reply mentioning "quota") that reader returns no jobs for a fixed 60 seconds, whatever wait time Google suggests. In the nightly run a fresh reader is created for each company, so the pause is not carried over to the next company, and the code that skips whole companies during the pause is not called by the nightly script. The pause is also not what stops a nightly run on a quota error, because on this path the reader quietly returns no jobs instead of raising the error that trips the run's quota alarm. What does carry across companies is the separate 60-second rest of an individual API key.
## 6
Every request goes to the main (free) key that has been used least, with the longest-unused key winning ties, so keys alternate even when nothing fails. When a key gets a rate-limit answer (429 or RESOURCE_EXHAUSTED), it is put aside for 60 seconds and the same request is retried on another key, for at most 3 tries, or 4 if a paid reserve key is configured, and fewer if there are fewer keys. Timeouts and other errors do not cause a switch.
## 7
Only when none of the five free keys is available because all five are in their 60-second rest after rate-limit answers, and the paid key is not itself resting. A single request makes at most 4 tries when a paid key exists, so a request where every free key fails would use four free keys and stop without touching the paid one. It would take a second request within that minute (the fifth free key fails, then all five are resting and the paid key is chosen). If the paid key is resting too, the pool goes back to the free key whose rest ends soonest.
## 8
The search runs in the browser over the companies already loaded. What you type is lowercased and split at commas, and a company matches if any of those words appears anywhere inside its name, its tags, its city or its sector name, ignoring capitals and matching part of a word, so "solar" would also match a name like "Solarwind" or a tag like "solar-pv". The description is not searched, and the result must also satisfy any sector, size, funding or hiring filters that are switched on.
## 9
The banner shows after the visitor has entered a website and pressed "AI Auto-fill", and the lookup finds a company in the directory whose website contains that domain and whose record is still a draft (awaiting review). It names the company, with its city if known, and says submitting will update the pending submission. Pressing Submit does not trigger it; if the match is a published company, the "Already Registered" warning shows instead, and a later auto-fill with no match clears the banner. The lookup takes the first company it finds and gives up after 3 seconds (no banner then), and an auto-fill result saved within the last 90 days can replay the earlier match without a fresh lookup.
## 10
The commit test-gate looks at the files staged for the commit, including deleted ones. It excuses markdown and text files, anything under docs, .memory, .agents, .claude or .github at the top of the repo, license files, .gitignore, .gitattributes, common image files, and symlinks and submodules. Every other staged file must match exactly the content recorded from the last passing test run, otherwise the commit is blocked. This only applies where the optional pre-commit hook has been installed.
## 11
It looks only at test files (for example files in a tests, test, __tests__ or spec folder, or named test_*, *_test.*, *.test.* or *.spec.*) and counts lines containing assertion calls such as assert, expect(, .should, raises( or toThrow, comparing the work to where the branch split from the default branch, uncommitted and new files included. It flags only when, across all changed test files together, more assertion lines were removed than added, and then it names each test file whose removals exceed its additions. An edited assertion line counts as one removed and one added, and removals offset by new assertions elsewhere in the same change are not flagged. A "tests-removed" row in the exceptions list on the default branch waives it.
## 12
It flags a coverage minimum being lowered (fail_under, --cov-fail-under, lines/branches/functions/statements in a jest or vitest config or package.json, or a codecov target) and a max-warnings limit or codecov threshold being raised, in the settings files it knows (pytest.ini, pyproject.toml, setup.cfg, tox.ini, .coveragerc, package.json, CI workflow files, and codecov.yml for the codecov ones). A setting removed with nothing put back is flagged too, while tightening is silent, a new setting with no old value removed is not flagged, and old and new values are compared across all files together, so moving the same value to another file is not flagged. A "threshold" row in the exceptions list on the default branch waives it.
## 13
Not "higher": the build validator fails only when a document's recorded content fingerprint differs from the one at the point the branch split from the default branch and its version number is exactly the same as before, so any different version, even a lower one, passes that check. It only checks documents that were already in the earlier manifest, and each version must be in x.y.z form. A separate release check on pull requests (the bump guard) does require the overall plugin version to be higher than the last release's when any shipped content has changed since that release.
## 14
It depends on which date line. The content fingerprint ignores only the version and timestamp lines in the top frontmatter block, so editing just a timestamp date does not count as a content change for the validator's per-document version check, although the manifest also records that date, so the separate release bump guard would still see a change. A date in the generated block (its "at" line, used by the memory templates) or a date written in the body of the document is not ignored and counts as a content change.
