## 1
A job goes live only when its confidence score is at least 85 out of 100 and none of these disqualifiers applies: an unusable or unreachable apply link, a talent-pool style title, a portal-only fallback link, a job category outside the approved list or a company flagged as unverified, or a location that looks foreign with no German match (a job classed as "other" is capped at 83, so it cannot reach 85). Anything under 85, or hitting one of those disqualifiers, is saved as a draft with the highest-ranked reason (unreachable link, foreign location, talent pool, portal fallback, unverified category, then missing details). Only a foreign location archives a job straight away, and not when the link is also unreachable, because the unreachable-link reason outranks it. After that, a re-scan never demotes a job that is already live; it is archived when it is missing from two scans of its company in a row (unless its link was refreshed), or by the link check that follows the nightly run when the page returns 404 or 410, says the position is filled or closed, fails twice, or was posted more than 180 days ago.
## 2
There is no separate 10-point item for the apply link itself: the 10 points go to a job unless its link was flagged as failing (a bad web response). The nightly adapters never flag a link as failing, so jobs get those 10 points by default. The link counts in other ways: it must be a valid http or https address or the whole score is 0, a valid link plus a valid title earns the 30 base points, and a link that looks like a direct job page adds 15 (otherwise 5; portal-fallback links are never treated as direct).
## 3
The title counts three times as much as the department. In each of the three keyword tiers a title match scores 15, 7.5 or 3.75, while a department match scores only 5, 2.5 or 1.25, and the department is counted for a tier only when the title did not already match that tier. The exception is the "avoid" keywords, which take off 15 whether they appear in the title or the department. The highest-scoring category wins, and if its score is below 4 the job is classed as "other"; several job sources pass no department at all, so for them only the title is used.
## 4
They come mainly from keyword matching on the job title, plus the source's own fields where the source provides them, such as the location or workplace type, an employment-type field, or a remote flag. For work mode the words are checked in the order remote, then hybrid, then on-site; job type and seniority are read from words such as full time, part time, working student, freelance, junior, senior, lead or director. If nothing matches, the saved job falls back to work mode hybrid, job type full time and seniority "experienced".
## 5
It is a 60-second "quota exhausted" flag on the Gemini AI extraction step, set when a Gemini call comes back as rate-limited (status 429, or an error mentioning quota) after the key pool has used its attempts. For those 60 seconds that extractor starts no new extraction and returns no jobs; it does not actually wait. In the nightly run every company gets a fresh extractor, so the flag only affects the company whose call failed and does not carry over to the next one, although each API key has its own separate 60-second cooldown that does carry over. This path returns an empty result rather than raising an error, so by itself it does not trigger the nightly run's quota stop and alert.
## 6
Before each request the pool picks the free key that has been used the least (ties go to the one used longest ago), so requests spread across the free keys instead of sticking to one. When a call comes back rate-limited (429), that key is put on a 60-second cooldown and the same request is retried with another key, for up to 3 attempts, or 4 when a paid reserve key is configured (fewer if there are fewer keys). Other problems such as timeouts or server errors do not make the pool switch keys.
## 7
The paid key is chosen only when every free key is in its 60-second cooldown from a rate-limit error and the paid key is not itself cooling down. With a paid key configured, one request tries at most 4 keys, so with five free keys a request that fails on four of them would give up before reaching the paid key; the paid key would come into play on a later request, once the fifth free key has also been rate-limited within the same 60 seconds. If the paid key is rate-limited too, the pool goes back to the free key whose cooldown ends soonest.
## 8
The typed text is lowercased and split at commas, and a company matches if any one of those terms appears anywhere inside its name, any of its tags, its city or its sector label. It is a plain "contains" check, not a whole-word match, it ignores capitals, and it does not look at the company description, so "solar" would match a name or tag such as "Solarfabrik" or "solar panels". The search is combined with the other directory filters (sector, team size, funding, hiring now), so a company has to pass both.
## 9
The banner shows after the visitor clicks AI Auto-fill with a website address and the lookup finds a company whose website contains that address's domain and whose status is "draft", meaning it was submitted earlier and is still in review. It names the company (with its city, if known), says the details were pre-filled, and says that submitting will update the pending submission. If the match has any other status, the "Already Registered" warning shows instead, and if there is no match, the lookup fails or takes longer than 3 seconds, neither shows. A lookup answered from the saved copy (kept up to 90 days) repeats the match stored at that time, so it would not reflect a later status change.
## 10
Only files staged for the commit are checked (not unstaged or untracked ones), compared with the last commit; a deleted file counts, and a rename counts as a delete plus an add. Each staged file must be exactly the version that was recorded when the related tests last passed, otherwise the commit is blocked until the tests are run again through the gate's record command. Skipped are documentation and text files (md, mdx, txt, rst), files under the top-level docs/, .memory/, .agents/, .claude/ and .github/ folders, LICENSE files, .gitignore, .gitattributes, image files (png, jpg, jpeg, gif, svg, webp, ico), and symlinks and submodules.
## 11
Only test files count: those in a tests, test, __tests__ or spec folder, named test_*, *_test.*, *.test.* or *.spec.*, or ending in Test.java or Tests.java. The guard compares, against the point where the branch left the default branch, how many assertion-style lines (assert, expect(, .should, raises(, toThrow and similar) were added and removed, and it flags only when the total across all changed test files is a net loss. When it is, it reports each test file that lost more assertion lines than it gained, a deleted test file included, while assertions added in other test files offset the loss in the total. A `tests-removed` exception row on the default branch's copy of the architecture file silences it for matching files.
## 12
It flags a loosening in the diff: a lowered or deleted coverage minimum (fail_under, --cov-fail-under, lines/branches/functions/statements for jest or vitest, or the codecov target), or a raised or deleted codecov threshold or --max-warnings / maxWarnings limit. Each setting is only looked for in its own config files (for example pytest.ini, pyproject.toml, setup.cfg, tox.ini, .coveragerc, package.json and workflow files; jest or vitest config; codecov.yml). It only fires when the old value shows up as a removed line, so a brand-new threshold is not flagged, tightening is silent, and a `threshold` exception row on the default branch silences it.
## 13
Partly. For each shipped document that already existed at the point where the branch left the default branch, the validator errors when its content fingerprint changed but its version is exactly the same as before. It only checks that the version differs, not that it is higher, it does not apply to documents that are new, and versions must be plain x.y.z numbers. A separate script, the release bump-guard, is what requires the overall plugin version to be higher than the last release tag's when shipped content changed since that tag.
## 14
It depends on the kind of date line. The content fingerprint ignores only the frontmatter lines whose key is `version` or `timestamp`, so changing just the older `timestamp:` line does not count as a content change. The newer `generated:` block's `at:` date is not ignored, so editing only that date does change the fingerprint and the validator then demands a different version number, as would a date written in the body.
