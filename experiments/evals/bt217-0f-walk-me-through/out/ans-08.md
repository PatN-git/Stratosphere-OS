## 1
Each scraped job gets a confidence score out of 100 and goes live only if it scores 85 or more and has none of these flags: an apply link that is invalid or known to be unreachable, a location abroad with no German match, an open-application or talent-pool title, a link that falls back to the company's general careers page, or an unverified category (a job category outside the official list, or one marked unverified). Otherwise it is saved as a draft labelled with its most serious reason, except that when the top reason is a foreign location it is archived straight away (most sources already drop non-remote jobs abroad before this step); one override beats all of this: if the same apply link is already live in the database, it stays live. A live job is archived later when its company's scan returns jobs but not this link, with no same-title job in the same region under a new link, for the second scan in a row. It is also archived by the link check (which only looks at live jobs not checked in the last 3 days, and is skipped on dry runs, after the AI quota circuit breaker trips, or when the run hits its time limit) if the page is gone (404/410), shows "position filled"-type text, the posted date is more than 180 days ago, or it gets a server error or other non-OK reply once its failure count reaches 2; network errors add to that count but never archive by themselves.

## 2
A job gets those 10 points unless its apply link is explicitly marked as known to fail; a link that was never checked still gets them. Before any points count, the link must be a valid http/https address and the title longer than 2 characters, otherwise the whole score is 0. In the code, no ingestion source ever marks a link as failing (a few mark it as working, the rest leave it unchecked), so in practice every scored job with a valid link gets these 10 points. They can still be cut off by the score caps (talent-pool titles max 75, careers-page fallbacks and unverified categories max 80, category "other" max 83); separately, the link earns 15 more points if it looks like a direct job posting, otherwise 5.

## 3
The department counts one third as much as the title: a keyword match in the title earns 1.5 times the base points (15, 7.5 or 3.75 depending on how strong the keyword is), the same match in the department only 0.5 times (5, 2.5 or 1.25). The department is only used for a keyword level when the title did not already match that level for that category, so the two never add up for the same level. The exception is a blocking word (for example "sales" for the data category), which costs the full 15 points whether it appears in the title or the department. Only some sources pass a department at all (Ashby, Personio, Recruitee, Workable, Join's category, the page scraper and the AI reader); for the others the title decides alone, and a final score below 4 becomes "other".

## 4
Each job source's reader fills them in from the job board's own fields where it has them (such as a workplace-type, employment-type or seniority field) and otherwise from the job title, using keyword lists: for example "remote" or "home office" gives remote, "hybrid" gives hybrid, "on-site", "vor ort" or "office" gives on-site, "Werkstudent" or "intern" gives working student, and "Director" or "VP" gives senior management unless it is an assistant role. Which fields are read differs per source; Greenhouse, for example, uses only the location text and title for work mode and only the title for seniority and job type, while the AI reader tries what the AI extracted first and the title second. If nothing matches, the saved job falls back to hybrid, full-time and "experienced". Where a source leaves a value blank, it first costs its confidence points (10 for work mode, 10 for job type, 8 for seniority), which can keep the job a draft; Deel, HeavenHR, Teamtailor, Recruitee and the page scraper fill some or all of these defaults before scoring.

## 5
When the AI page reader gets a quota error (HTTP 429, or an error whose details contain "quota"), it stops for that company with no jobs and marks itself paused for a fixed 60 seconds, ignoring any wait time the AI service suggests. In the nightly run that pause covers only that one company: every company gets a brand-new reader, so the next company's AI call is not held back. The quota error also does not trip the nightly run's quota circuit breaker, because the reader returns an empty result rather than an error, so the run carries on with the next company. What does carry over for the rest of the run is the key pool's own 60-second cooldown on the specific key that hit the limit.

## 6
On every call the pool hands out the least-used free key that is not cooling down (on a tie, the one used longest ago), so calls rotate across the free keys even without errors. It switches away from a key in the middle of a request only when that call is rate-limited (HTTP 429, or an error mentioning 429 or RESOURCE_EXHAUSTED): the key goes into a 60-second cooldown and the request is retried on another key, up to 3 tries in total (4 if a paid backup key is set), and never more tries than there are keys. Other failures, such as timeouts, server errors or a model not found, are not retried on another key by the pool. If all free keys are cooling down it uses the paid backup key, and if that is cooling too, the free key whose cooldown ends soonest.

## 7
The paid key is tried only when all five free keys are in their 60-second cooldown after a rate-limit error (and the paid key is not cooling down itself); then even the first try of a new request goes to it. With six keys one request makes at most 4 tries, so a single request can cool down at most 4 free keys and gives up before reaching the paid key; it reaches the paid key only if at least two free keys were already cooling down from earlier requests when it started. Note that the nightly job workflow passes only the GEMINI_API_KEY setting and none of the paid-key settings (GEMINI_BACKUP_KEY, GEMINI_PAID_KEY or GEMINI_API_KEY_BACKUP), so the nightly run has no paid key configured through that file.

## 8
The search splits what you type at commas, and a company is shown if any one of those terms appears, ignoring upper/lower case, anywhere inside its name, its tags, its city or its sector's label. So "solar" is a plain "contains" match: it would match a company named "Solarwatt", a tag like "solar thermal", or "solar" inside a longer word, but it does not search the company description, and spaces do not split terms ("solar storage" would be searched as one phrase). The search is combined with the other filters (sector, team size, funding, hiring now), so a company must pass those too.

## 9
The banner appears only after someone clicks the auto-fill button for a website and the answer includes an existing company whose status is "draft" (a submission still in review); if the matched company has any other status, the "Already Registered" banner shows instead. The match is the first company whose stored website contains the entered domain, ignoring "www." and upper/lower case. If that website was looked up in the last 90 days, the answer comes from a saved copy, so the banner reflects whether a draft existed when that copy was saved, not necessarily now. The banner stays until the next successful auto-fill replaces or clears it; editing the website field alone does not remove it.

## 10
When the commit hook is installed, it checks every file staged in the commit, compared with the last commit (deletions included), and blocks the commit if any of them does not exactly match the content recorded from a passing test run. It skips documentation and framework files: anything ending in .md, .mdx, .txt or .rst, anything under docs/, .memory/, .agents/, .claude/ or .github/ at the repo root, LICENSE files, .gitignore, .gitattributes, images (.png, .jpg, .jpeg, .gif, .svg, .webp, .ico), symlinks and submodules. Everything else that is staged, such as code, tests, configs and scripts, is checked. The name matching is case-sensitive, so a file ending in ".MD" would be checked.

## 11
It flags them when, across all test files in the change (everything since the branch left the default branch, including uncommitted and new files), more lines containing an assertion were removed than added. It then names each test file that lost more assertion lines than it gained; if the overall total did not drop, nothing is flagged, even if one file lost assertions. It counts lines, not individual assertions, using markers such as assert…, expect(, .should, raises( and toThrow, and a test file is one under a tests/test/__tests__/spec(s) folder or named like test_*, *_test.*, *.test.* or *.spec.*. A flagged file is excused only by a matching "tests-removed" row in the Floor exceptions section of .memory/ARCHITECTURE.md as it stands on the default branch.

## 12
It flags one only when the change removes a line that set it and the new value is looser or missing: a coverage minimum (fail_under, --cov-fail-under, Jest/Vitest lines/branches/functions/statements, Codecov target) is flagged if lowered or deleted, and a max-warnings limit (--max-warnings or maxWarnings) or Codecov threshold is flagged if raised or deleted. Tightening a value, or adding a setting where none existed before, is silent. It only looks in specific files: pytest.ini, pyproject.toml, setup.cfg, tox.ini, .coveragerc, package.json and .github/workflows files for fail_under and max-warnings; Jest/Vitest config files and package.json for lines/branches/functions/statements; and codecov.yml for target and threshold, so a max-warnings limit kept in, say, an ESLint config file would not be checked. A matching "threshold" row in the Floor exceptions section of .memory/ARCHITECTURE.md on the default branch excuses it.

## 13
No, it only requires the version to be different. For each shipped document in the built manifest, if its content fingerprint differs from the one at the point where the branch left the default branch and its version is exactly the same, it fails with "content changed but version not bumped"; any different version passes, even a lower one, as long as it has the x.y.z form. Documents that are new since that point are not checked for a bump at all. A separate release check on pull requests does require the overall plugin version to be higher than the last release when shipped content changed, but that is the plugin's number, not each document's.

## 14
It depends on which date line. The fingerprint leaves out only the "version" and "timestamp" lines at the top of a document, so editing just a timestamp line does not count as a content change. Documents that keep their date as an indented "at:" line under "generated:" (for example the ARCHITECTURE.md memory template) are fingerprinted with that line included, so changing only that date does count, and the validator would then require a different version. A date written anywhere in the document's body also counts as content.
