## 1
A scraped job goes live only when its confidence score is at least 85 out of 100 and none of the disqualifiers apply: an unreachable or invalid link, a location outside Germany, a generic talent-pool title, a fallback link to the company's general portal, or an unverified sector or job category. Otherwise it is saved as a draft with the highest-ranking reason, except a job in a foreign location, which is saved as archived (an unreachable link outranks that, so it stays a draft). A job that is already live is not demoted by a later re-scan. A live job is archived later when it is missing from its company's scan twice in a row (only counted when that scan found at least one job), or when the daily link check finds a 404/410 or a "position filled" style page, a second failed check in a row for a server error or other non-OK reply, or a posting date more than 180 days old; a network timeout leaves it unchanged.
## 2
The score adds 10 points unless the job's link is explicitly flagged as not reachable. In the nightly code that flag is only ever set to "reachable" by a few adapters and is otherwise left unset, so a valid link normally gets the 10. If the apply link is not a valid web address (http or https) the whole score is 0 instead; separately, a link that looks like a job page (not a fallback to the company portal) gets 15 more points, otherwise 5.
## 3
The department counts one third as much as the title: a keyword match in the title scores 15, 7.5 or 3.75 depending on how strong the keyword list is, while the same match in the department scores 5, 2.5 or 1.25. The department is only used for a keyword list the title did not already match, and a department match can also trigger the same 15-point penalty as the title. A category needs at least 4 points, otherwise the job becomes "other". Only some job sources pass the department in (for example Ashby, Personio, Recruitee, Workable, Join, the AI reader and the generic page reader); Greenhouse, HeavenHR, HiBob, Deel, TalentStorm and Teamtailor score on the title alone.
## 4
They are not typed in by anyone. The importer reads them from the hiring system's own fields where that system offers one (for example a workplace-type or employment-type field), and otherwise looks for English and German keywords in the job title, using shared keyword rules; which field is used depends on the job source. If nothing matches, the value is left blank when scored (costing points), and when the job is saved it is filled in as hybrid, experienced and full time. A few sources fill some of those defaults in earlier (Teamtailor and HeavenHR for work mode and job type, Deel for all three), and Recruitee and the generic page reader assume all three only for the score, so for those the blank costs no points.
## 5
It is the Gemini extractor's own timer: when Gemini answers with a quota (429) error, or a reply mentioning "quota", the extractor starts a fixed 60-second pause (it does not use Gemini's own retry-after value) and returns no jobs for that company. In the nightly run, though, each company gets a freshly built extractor with its own timer, so the pause does not carry over to the next company and does not stop the run; the run's quota alert and stop only fire when a company's extraction throws a 429-type error, which this path does not. The company is still counted as checked in a normal run. What does carry across companies is the separate 60-second per-key cooldown in the shared Gemini key pool.
## 6
Each call normally uses the least-used free key that is not cooling down (ties go to the one used longest ago), so keys rotate even without errors. When a call gets a 429 or a "resource exhausted" error, that key is put on a 60-second cooldown and the same request retries with another key, up to 3 attempts (4 if a paid reserve key is set, and never more than the number of keys); the last failure is passed on as a 429. Other errors such as a timeout do not trigger a switch.
## 7
The paid key is used only when no free key is available, meaning all of them are on their 60-second cooldown, and the paid key itself is not cooling down. Because a single request makes at most 4 attempts when a reserve key exists, a request that starts with all five free keys fresh fails after four free keys without reaching the paid one; the next request has four on cooldown, uses the fifth, and only after that fails does the paid key come into play. If the paid key is also cooling down, the free key whose cooldown ends soonest is used. The nightly workflow only passes in GEMINI_API_KEY, not a reserve-key setting.
## 8
It is a simple "contains" match on what was typed, ignoring upper and lower case: "solar" matches any company whose name, tags, city or sector label has those letters inside it. Several words separated by commas match if any one of them matches. The description is not searched, and none of the built-in sector labels contains "solar". The search applies together with any sector, team size, funding or hiring filters that are on.
## 9
Only after the visitor clicks "AI Auto-fill", when the server finds a company already stored with a website containing the same domain (the first match only) and that company's status is "draft". If the matching company has any other status it shows "Already Registered" instead, and if no match is found, the lookup fails or runs over 3 seconds, or the database is not configured, no such banner appears. When the answer comes from the 90-day saved cache, the match saved with it is shown, which could be out of date.
## 10
It checks the files staged for the commit being made (compared with the last commit), not the whole working folder. Each staged file must be in the record of the last passing test run with exactly the same content, so a file edited after that run, a new file, or a deletion not in the run blocks the commit. Not checked: .md, .mdx, .txt and .rst files, anything under docs/, .memory/, .agents/, .claude/ and .github/, LICENSE files, .gitignore, .gitattributes, common image files (png, jpg, jpeg, gif, svg, webp, ico), symlinks and submodules. It only runs where its pre-commit hook has been installed.
## 11
It compares the branch (committed, staged, unstaged and new files together) with where it split from the main branch, and looks only at test files, such as those in test, tests, spec or __tests__ folders or named test_*, *_test.*, *.test.* or *.spec.*. It counts lines that look like assertions (for example assert, expect(, .should, raises(, toThrow) added versus removed across all test files, and flags only when the total ends up lower, listing each test file that lost more than it gained. Assertions that are moved or rewritten with no net loss, or offset by new ones elsewhere, are not flagged, and a "tests-removed" exception row already merged on the main branch for that file path silences it.
## 12
It flags a quality limit that got looser compared with where the branch split from main: a minimum coverage figure going down (fail_under, --cov-fail-under, or lines/branches/functions/statements in a jest or vitest config or package.json, or a codecov target), or a max-warnings limit going up (--max-warnings, maxWarnings, or a codecov threshold). Deleting such a setting without putting one back also counts; adding a new one, or making a limit stricter, does not. It only looks in the files each setting normally lives in, such as pytest.ini, pyproject.toml, setup.cfg, tox.ini, .coveragerc, package.json, the GitHub workflow files and the codecov file. A "threshold" exception row merged on the main branch for that path silences it.
## 13
Not strictly higher. For each built document that already existed where the branch split from main, the validator only fails when the document's content fingerprint changed and its version number is exactly the same as then; any different version passes, even a lower one, as long as it is in x.y.z form. New documents are not checked this way. A separate script (the release bump guard) does require the whole plugin's version to be higher than the last release when shipped content has changed.
## 14
Only if it is the "timestamp:" line at the top of the file. The validator's fingerprint ignores the version and timestamp lines in the top metadata block and counts everything else, so changing just that one line needs no version bump. Other date lines do count: the "at:" date under "generated:" (used in the memory templates) and any date written in the body text.
