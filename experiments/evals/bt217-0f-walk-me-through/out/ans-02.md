## 1
Each job gets a 0-100 confidence score, and it goes live only if the score is 85 or more and none of these disqualifiers apply: the link is unreachable or not a web address, the title is a generic talent-pool or open application, the link is a portal fallback rather than a direct apply link, or the taxonomy is unverified. Talent-pool titles, portal fallbacks and unverified taxonomy also cap the score below 85 (at 75, 80 and 80), and any disqualified job is a draft even if its score reached 85; missing fields alone do not block live if the score is 85 or more. A job is stored as archived only when foreign location is its top-ranked problem: the location text does not match a German region, Germany or Deutschland, the job has no region assigned, and the location matches the foreign list. An unreachable link outranks that and gives a draft instead. After ingestion, a job already stored as live is never demoted by a re-scan, and it can later be archived by the daily link check (404/410, "position filled" page text, two failed checks in a row, older than 180 days) or when it is missing from two consecutive scans.
## 2
The 10 points are given when the job is not flagged as having a failing link: the code adds them unless the "link works" flag is explicitly false, so an unset flag still earns them. This is only reached if the apply link is a valid web address (http or https); otherwise the whole score is 0. In the connectors I traced, that flag is either set to true or left unset, and I found nothing that sets it to false. Separately, a link that looks like a direct job page earns 15 points rather than 5.
## 3
The department counts one third as much as the title: a match in the title is worth 15, 7.5 or 3.75 points depending on the tier of the phrase, while the same match in the department is worth 5, 2.5 or 1.25. The department is only used for a tier when the title did not already match that tier, and a "blocking" phrase in either the title or the department subtracts 15 from that category. The best category needs at least 4 points or the job is labelled "other", so on its own a department needs a top-tier phrase match to get there. Only some connectors pass the department in (for example Ashby, Personio, Recruitee, Workable, Join, the page-selector and AI extractors); others such as Greenhouse, HiBob and Teamtailor score on the title alone.
## 4
They are worked out by keyword rules applied to the text each job source provides, such as the title, the location text, and fields like workplace type, employment type or seniority where that source has them. The AI extractor's answers are run through the same rules, with the title as a second try. If no rule recognises anything, the job row is filled with defaults: seniority "experienced", job type "full time" and work mode "hybrid". The confidence score only credits values the connector actually found, not these defaults.
## 5
The pause is held by the single AI extractor object that hit the error, and while it lasts that object returns no jobs. In the nightly run a fresh extractor is created for each company, so the pause effectively covers only the company being processed, not the rest of the batch. It is a fixed 60 seconds, not the wait time the service suggests. The nightly run uses the batch routine that does not check this pause before moving to the next company; the separate Gemini key pool has its own 60-second pause per key that is shared across companies.
## 6
A key is switched out when a request on it comes back as a quota error (HTTP 429 or "resource exhausted"): that key is put in a 60-second pause and the request is retried on another key. A single request makes at most 3 attempts, or 4 if a paid reserve key is configured, capped at the number of keys; after that it reports the 429. Separately, before each request the pool picks the free key with the fewest uses so far (oldest last use breaks ties), so usage rotates even without errors. Other failures, such as a timeout or a 503, do not trigger a key switch.
## 7
The paid reserve key is used only when no free key is available, meaning all of them are in their 60-second pause, and the paid key is not itself paused. A single request starting with all five free keys healthy makes at most 4 attempts, so it would use up four free keys and not reach the paid one; the fifth free key would fail in a following request, and the next attempt would then go to the paid key. If the paid key is also paused, it goes back to the free key whose pause ends soonest. The nightly workflow file only passes GEMINI_API_KEY, with no reserve-key variable, so a paid key would have to be added there.
## 8
The search is a case-insensitive "contains" match, not a whole-word match, so "solar" matches any company whose name, tags, city or sector label has "solar" anywhere inside it (for example inside a longer word). The typed text is lowercased and trimmed; commas split it into several terms, and a company matches if any one term appears in any of those four fields. It does not search the description. An empty search shows everyone, and the search combines with any sector, team size, funding or hiring filters that are also set.
## 9
The banner appears only after the visitor has clicked "AI Auto-fill" with a website entered, and the lookup then finds an existing company whose website contains that domain and whose status is draft. The first match found is the one used. If that company has any other status, the "Already Registered" banner appears instead, and if no company is found, or the lookup fails or exceeds its 3-second limit, neither banner appears. An answer served from the 90-day lookup cache reuses what was saved earlier, so the banner reflects the company's status at that time.
## 10
It checks the files staged for the commit that differ from the last commit, deletions included. Exempt files are skipped: markdown, text and .rst files, images (png, jpg, jpeg, gif, svg, webp, ico), LICENSE files, .gitignore, .gitattributes, the top-level docs, .memory, .agents, .claude and .github folders, and links or submodules. Every other staged file must appear in the record of the last passing test run with exactly the same content, or the commit is blocked.
## 11
The guard counts lines that look like assertions in test files, across the whole change from where the branch left the main branch to the current working files, including uncommitted and new files. It flags only when the total of added minus removed assertion lines across all test files is below zero, and then it lists the test files that lost more than they gained. So removing assertions in one file is not flagged if another test file gains at least as many, and an edited assertion line counts as zero. A row for "tests-removed" in the exceptions list on the main branch's latest version can approve it.
## 12
It flags a loosening, not a tightening: a coverage minimum (such as fail_under, --cov-fail-under, or lines/branches/functions/statements, or the Codecov target) that is lowered or removed, or a max-warnings limit (or Codecov threshold) that is raised or removed. The guard looks only at the settings files it knows (for example pytest.ini, pyproject.toml, setup.cfg, tox.ini, .coveragerc, package.json, jest/vitest config, codecov.yml, and GitHub workflow files), and it needs an old line removed in the change, so adding a brand-new limit is not flagged. A "threshold" row in the exceptions list on the main branch's latest version can approve it.
## 13
Not "higher": the validator only requires that the version differs from the one at the point the branch left the main branch. For each bundled document that existed then, if the stored content fingerprint changed but the version number is the same, it reports "content changed but version not bumped". Every version must also be in the form x.y.z, and documents that did not exist at that point are not checked. A separate release check (bump_guard) does require the whole plugin's version to be higher than the last release when shipped content has changed.
## 14
It depends on which date line. The content fingerprint ignores only the lines named version and timestamp in the top frontmatter block, so editing a `timestamp:` date line does not count as a content change. Documents that carry a `generated:` block with an `at:` date, such as the PRD template and the ARCHITECTURE memory template, are different: the `at:` line is not ignored, so editing it does count and needs a version bump.
