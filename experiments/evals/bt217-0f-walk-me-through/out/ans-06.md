## 1
At ingest, a job is saved as live when its confidence score is at least 85 out of 100 and none of these apply: no valid web apply link or a link flagged as failing, a foreign location, a talent-pool or open-application title, a company portal page standing in for a direct link, or an unverified job category. Otherwise it is saved as a draft, labelled with the highest-ranked problem (dead link first, then foreign location, talent pool, portal page, unverified category, missing details); the exception is a foreign location (counted only when nothing ties the job to Germany) that is the top-ranked problem, which is saved as archived instead. A job already live under the same apply link stays live even if the new scan would have made it a draft. Live jobs are archived later when a company scan that finds at least one job misses them twice in a row, or when the link check (live jobs not checked in the last 3 days) finds no link, a posting older than 180 days, a 404/410 or "position filled" style page, or a second failed check without a healthy one in between; drafts are not touched by either.

## 2
The 10 points are a "link is not known to be dead" bonus in the confidence score: a job gets them unless its record explicitly says the link failed. Nothing in the ingestion code sets that failure flag (only tests do), so a job with a valid http/https link gets the 10 points, while a job with no valid link gets a total score of 0 instead. The link also counts elsewhere: it is part of the 30-point base, and it earns 15 more points if the address looks like a direct job page, otherwise 5.

## 3
A department match counts one third of a title match: for the three keyword strengths a title hit is worth 15, 7.5 and 3.75 points, and a department hit 5, 2.5 and 1.25. The department only adds points for a given keyword strength when the title did not already match it, while the penalty for a conflicting keyword is the same 15 points whether it comes from the title or the department. A category needs at least 4 points to win, otherwise the job is "other", so a department hit on the strongest keyword alone would be enough but a weaker one alone would not. Only some job sources pass the department (Ashby, JOIN, Personio, Recruitee, Workable, the AI reader and the page-selector reader); Greenhouse, Deel, HeavenHR, HiBob, TalentStorm and Teamtailor classify from the title alone.

## 4
Each job source reads them from its own feed fields where it has them (for example Ashby's workplace type and employment type, Recruitee's remote flag and codes, Workable's remote flag and type, Personio's schedule), and otherwise from keywords in the job title, sometimes also the location text. Seniority comes from the title keywords for most sources; only Personio, Recruitee, TalentStorm, Workable and the AI page reader also use a seniority or experience field from the source. If nothing is found, the saved job gets the defaults hybrid, experienced and full-time (some sources, such as Deel, HeavenHR and Teamtailor, apply hybrid or full-time themselves).

## 5
The pause is set inside the AI extraction step when Gemini answers with a rate-limit error (429) or a reply that mentions "quota"; for 60 seconds that step then returns no jobs without calling Gemini. In the nightly run a fresh AI step is built for each company, so the pause is not carried to the next company and only covers the rest of that one company's extraction. The 60 seconds is fixed (the provider's retry-after value is not used for it). Because the step returns an empty list instead of raising an error, it does not set off the nightly run's own quota stop, which only fires when an extraction raises a 429 error.

## 6
Before each call the pool picks, among the free keys not currently cooling down, the one used least so far (ties go to the one used longest ago), so usage rotates even without errors. It also switches after a key returns a 429 or an error naming 429 or RESOURCE_EXHAUSTED: that key is put on a 60-second cooldown and the call is retried on another key, up to the smaller of the number of keys and 3 attempts (4 when a paid reserve key exists). Other failures, such as timeouts or other error codes, do not cause a switch, and if the last attempt also gets a 429 the call fails with a 429.

## 7
The paid reserve key is chosen only when none of the five free keys is eligible, meaning all five are in their 60-second cooldown after 429s, and the paid key itself is not cooling. When a reserve key exists a single request makes at most 4 attempts, so a request that starts with all five free keys healthy would spend its attempts on free keys and fail without reaching the paid key; it would reach it only if at least two free keys were already cooling from earlier calls. If the paid key is also cooling, the pool picks the free key whose cooldown ends soonest rather than the paid one. The nightly workflow file passes only GEMINI_API_KEY and none of the reserve-key settings.

## 8
The typed text is lowercased and split at commas, and a company matches if any one of the pieces appears anywhere inside its name, one of its tags, its city or its sector label. It is a plain "contains" match, not a whole-word or fuzzy match, so "solar" would also match a name or tag that merely contains those letters. The company description is not searched, and the search combines with the sector, team size, funding and hiring filters, which must all pass as well.

## 9
The "Submission in Review" banner appears only after the visitor clicks "AI Auto-fill" and the answer says the company already exists in the directory with a draft status; the match is the first company record whose website contains the same domain. If that record is not a draft the "Already Registered" warning shows instead, and if no record is found, the lookup fails or takes longer than 3 seconds, or auto-fill is not run, there is no banner. An auto-fill answer served from the 90-day cache is not re-checked and repeats whatever existing-company result was saved with it.

## 10
It checks the files staged for the commit, compared with the last commit (a rename counts as a delete plus an add), and each one must match exactly the content that was present when a passing test run was last recorded; a staged deletion needs a recorded run where the file was already gone. It skips files tests do not cover: Markdown and text files (.md, .mdx, .txt, .rst) and common image files at any depth, LICENSE files, .gitignore and .gitattributes, everything under docs/, .memory/, .agents/, .claude/ and .github/, plus symlinks and submodules. Any other staged file that is missing from the record or differs from it blocks the commit, provided the pre-commit hook is installed.

## 11
It compares your changes (since the branch forked from the default branch, including uncommitted and untracked files) in test files only, counting lines that contain an assertion such as assert, expect( or toThrow. It flags only when the total of added assertion lines minus removed ones across all changed test files is below zero, and then reports each test file that lost more than it gained. Moving assertions between test files or rewriting them in place nets to zero and is not flagged, and a deleted test file counts its assertion lines as removed. A "tests-removed" exception row for that file path, already merged into the default branch's architecture memory file, silences it.

## 12
It flags it when, in those same changes, a line holding one of these limits is removed and is either not replaced or replaced by a looser value: a coverage minimum lowered (fail_under or --cov-fail-under in pytest.ini, pyproject.toml, setup.cfg, tox.ini, .coveragerc, package.json or workflow files; lines, branches, functions or statements in jest/vitest config or package.json), a codecov target lowered or threshold raised, or a --max-warnings / maxWarnings limit raised. Raising a minimum, lowering a maximum, adding a brand-new limit, or moving the same setting from one file to another is not flagged. A "threshold" exception row for that file path, merged into the default branch's architecture memory file, silences it.

For each Markdown document in the built bundle that already existed at the point the branch forked from the default branch, validate.py fails when its content fingerprint changed but its version is exactly the same as before; any different version, even a lower one, passes that check, and every version must just have the x.y.z form. ## 14
It depends on which date line. The content fingerprint leaves out only the header lines named version and timestamp, so changing only a "timestamp:" date, as skill files carry, does not count as a content change. A date under "generated: at:", as the memory templates carry, is not left out, so editing only that line changes the fingerprint and the validator then requires the version to change; a date written in the body text counts as content as well.
