## 1
Each ingested job gets a confidence score out of 100: at 85 or more it goes live, below 85 it is saved as a draft. Even at 85 or more it stays a draft if its link is unreachable, it is an open-application/talent-pool posting, it only links to the company's portal, or its category or company is unverified; it is archived straight away if its main problem is a non-German location (an unreachable link outranks that and keeps it a draft). Override: a job whose apply link is already live in the database stays live on re-scan, whatever the new score. A live job is archived later if its company's feed returns jobs but leaves this one out on two scans in a row, or if the daily link check finds a 404/410, "position filled" text, an error reply right after an earlier failed check, or a posting older than 180 days.

## 2
The 10 points are given unless the job's link is marked as known to fail ("is_http_200" set to false), and in the current ingestion code nothing sets that flag to false: connectors either set it to true or leave it empty. So in practice every job that gets scored receives them, but a title of 2 characters or fewer, or an apply link that is not a valid http/https address, makes the whole score 0. This is separate from the 15 points (or 5) for a direct job link versus another link. Caps can still cut the total afterwards, for example to 75 for a talent pool or 80 for a portal-only link.

## 3
The department counts one third as much as the title: a strong keyword match scores 15 in the title but 5 in the department, a medium one 7.5 against 2.5, and a weak one 3.75 against 1.25, and the department only counts for a level the title did not already match in that category. A blocking word (for example "sales" ruling out data/AI) takes off 15 points whether it is in the title or the department. The highest-scoring category wins, and below 4 points the job is labelled "other". Several connectors (Greenhouse, HiBob, Teamtailor, TalentStorm, HeavenHR, Deel) pass no department at all, so for those jobs only the title counts.

## 4
Each job-board connector reads them from the posting's own fields when the board provides them (for example workplace type or location, employment type, seniority) and otherwise from keywords in the job title; for AI-read career pages it uses the AI's answer first, then the title. One shared keyword matcher turns that text into values: "remote" or "home office" means remote, "hybrid" means hybrid, "on-site", "vor Ort" or "office" means on-site, and words like intern/student, director/VP/chief, head of, team lead, junior or senior set the seniority. When nothing matches, the saved job falls back to hybrid, experienced and full-time, but it has already missed the score points for those fields and is flagged as missing details. Exception: a few connectors (Deel, for example) fill in those defaults before scoring.

## 5
When the AI extractor gets a quota error (a 429, or a reply mentioning "quota"), it stops trying other AI models for that company, returns no jobs for it and starts a 60-second pause. That pause belongs to the extractor, and the nightly run builds a new extractor for each company, so it only covers the company that hit the error: the next company starts with no pause. The error is handled quietly rather than raised, so it does not trigger the run's quota circuit breaker, which would stop the whole batch. The failing key is also benched for 60 seconds in the shared key pool, but the nightly workflow only passes GEMINI_API_KEY, and if that holds a single key the pool hands out the same key anyway.

## 6
The pool switches keys on every AI call even without errors: it hands out the free key used least so far (ties go to the one used longest ago), skipping keys still in their 60-second bench. During a call it switches only after a rate-limit error (a 429, or an error message containing "429" or "RESOURCE_EXHAUSTED"): the failing key is benched for 60 seconds and the call retries on another key, up to 3 tries (4 if a paid backup key is set) and never more than the number of keys. Other failures, including timeouts, are not retried on another key. If every free key is benched, it uses the paid key if that one is not benched, otherwise the free key whose bench ends soonest.

## 7
The paid key is tried only when all five free keys are benched at that moment (each hit a rate limit in the last 60 seconds) and the paid key itself is not benched. One AI call makes at most 4 tries, so with five fresh free keys a call would try four free keys and, if all four are rate-limited, fail without reaching the paid key. A next call within 60 seconds would try the fifth free key and only then the paid key. As soon as a free key's 60 seconds are up, it is preferred over the paid key again.

## 8
The search box splits what you type at commas into separate terms, trims them and ignores upper/lower case. A company matches if any term appears anywhere inside its name, tags, city or sector label, so "solar" would match a name like "Solarize" or a tag like "solar energy", not only an exact "Solar". Other text, such as the description, is not searched. The search is combined with the other active filters, which a company must also pass, and an empty search box shows every company.

## 9
The banner appears after the user clicks "AI Auto-fill" and the reply names an existing company whose status is draft. The server looks for a company whose website contains the entered domain (lower-cased, "www." removed) and takes the first match. If the match is already published, the "Already Registered" banner shows instead, and no banner shows if nothing matches or the lookup fails or takes more than 3 seconds. Exception: if the auto-fill result comes from the 90-day cache, no new lookup runs and the banner reflects the match saved with that cached result.

## 10
Before a commit, the gate checks the files staged for it (compared with the last commit), including deleted files, but not unstaged changes. It skips docs and non-code files: names ending in .md, .mdx, .txt or .rst, LICENSE files, .gitignore, .gitattributes, images (png, jpg, jpeg, gif, svg, webp, ico), anything under the top-level docs/, .memory/, .agents/, .claude/ or .github/ folders, plus symlinks and submodules. Every other staged file must be exactly the version recorded at the last passing test run, or the commit is blocked. It only runs where its pre-commit hook is installed.

## 11
The floor guard compares your branch, including uncommitted and new files, with where it split from the default branch, and in test files counts the added and removed lines that contain an assertion (assert, expect(, should, raises(, toThrow and similar). It flags only when, across all changed test files together, more assertion lines were removed than added, and then lists each test file that lost more than it gained. Moving assertions from one test file to another therefore balances out. A flagged file passes only if a "tests-removed" exception row covering it is already merged on the default branch.

## 12
It flags only a change that loosens an existing setting: a coverage minimum lowered or removed, or a warning or threshold limit raised or removed; tightening, or adding a setting that was not there before, is not flagged. Coverage minimums are read from Python config files, package.json and GitHub workflow files (fail_under, --cov-fail-under), from Jest/Vitest config or package.json (lines, branches, functions, statements), and from codecov.yml (target, plus threshold, where higher is looser). The max-warnings limit (--max-warnings or maxWarnings) is only read from those Python config files, package.json and workflow files, not from a separate ESLint config. A flagged change passes only with a "threshold" exception row already merged on the default branch.

## 13
No, the build validator requires a different version number, not a higher one. For each shipped document that already existed where the branch split from the default branch, it reports an error if the content changed but the version is still identical, so a lower number would pass. Documents that are new since then are not checked, though every version must have the x.y.z format. Only the separate release check, run on pull requests, requires a higher number, and only for the whole plugin version: if shipped content changed since the last release, that version must be above the release's.

## 14
It depends which date line. Before comparing, the validator ignores only the header lines named "version" and "timestamp", so editing just the "timestamp:" line is not a content change. A date anywhere else does count, including the "at:" line under the newer "generated:" header block that some documents (such as the memory templates) use, and any date in the body. Differences only in line endings or a byte-order mark are also ignored.
