## 1
Each night a job read from a company's career page is scored, and it goes live only if the score is at least 85 and nothing disqualifies it: a broken or missing apply link, a non-German location, a generic "open application" or talent-pool title, a link that only goes to the company's general portal, or an unverified category. If it fails that test it is saved as a draft, except that a foreign-location job is archived (a broken link takes priority over foreign location, so that one stays a draft). A job already live under the same apply link is never pushed back to draft or archived by a re-scan. Afterwards a live job is archived if it is missing from two scans in a row (only counted when that company's scan found at least one job), and the daily link check archives live jobs whose link has no address, whose posted date is over 180 days old, that return "not found" or "gone", that show "position filled" style text, or that fail twice (server error or another non-OK reply); a failed network connection alone does not change the status.

## 2
The 10 points are given to any job whose link is not known to be broken. The score first requires a title longer than 2 characters and a valid web link (http or https); without a valid link the job scores 0. A job with a valid link then gets the 10 points unless the data explicitly says the link did not load, and nothing in the ingestion code I read sets that to false. Separately, the link earns 15 more points if it looks like a direct job page (for example it contains /jobs or /careers) and not a portal fallback, otherwise 5.

## 3
The department counts one third as much as the title. A keyword in the title earns 15, 7.5 or 3.75 points depending on how strong the keyword list is, while the same keyword found in the department earns 5, 2.5 or 1.25. The department is only used for a strength level the title did not already match, and a "wrong category" word in either the title or the department takes 15 points off. The best category needs at least 4 points, otherwise the job is labelled "other", and only some job-board readers (for example Ashby, Personio, Recruitee, Workable) pass the department in at all; Greenhouse and several others score on the title alone.

## 4
They are worked out by keyword rules applied to what the job board provides: the title and location, plus board-specific fields where they exist (for example Ashby's workplace type and employment type, or Personio's schedule, seniority and years-of-experience fields). For pages read by the AI, the AI's answer is tried first and then the title. If the rules find nothing, the saved job gets defaults: seniority "experienced", job type "full time" and work mode "hybrid". The confidence score only counts values the rules actually found, so those defaults earn no points.

## 5
After the AI page reader gets a quota error (an HTTP 429 reply, or any failed reply whose text mentions "quota"), it sets a fixed 60-second pause and returns no jobs for that company. During those 60 seconds that same reader skips AI extraction without calling the AI. In the nightly run, however, a new reader is created for each company, so the pause covers only that one reader and does not carry over to the next company; it also does not stop the run, because the run's quota stop needs a raised 429 error and this reader returns an empty result instead. The separate 60-second cooldown per API key (next question) is shared across the whole run.

## 6
The pool moves between keys in two ways. On every call it picks the free key used the fewest times (ties go to the one used longest ago), skipping any key that is cooling down, so use rotates even without errors. When a call comes back with a rate-limit error (429), that key is put on a 60-second cooldown and the same request is retried with another key. Other errors, such as a timeout or a server error, do not trigger a switch, and one request makes at most 3 attempts (4 if a paid reserve key is configured), or fewer if there are fewer keys.

## 7
The paid key is chosen only when none of the five free keys is available because all of them are in their 60-second cooldown after a rate-limit error, and the paid key itself is not cooling down. Within a single request starting from a clean slate this cannot happen, because at most 4 attempts are made and each rate-limit error cools only one free key, so the paid key typically gets used on a later request within the same minute. As soon as a free key's cooldown ends, the pool goes back to the free keys. If the paid key also hits a rate limit it gets its own 60-second cooldown, and when every key is cooling the pool falls back to the free key whose cooldown ends soonest.

## 8
The typed text is matched as a plain, case-insensitive "contains" check, so "solar" matches any company whose name, any of its tags, its city or its sector label includes the letters "solar" (including as part of a longer word). Commas split the search into several terms, and a company matches if any one term is found in any of those fields; a space does not split terms. The company description is not searched. The search is combined with the sector, team size, funding and hiring filters, so a company must pass those as well.

## 9
The banner appears after the user enters a website and clicks "AI Auto-fill", and only when the lookup finds an existing company whose website contains that domain and whose status is "draft". Only the first matching company is considered, and a match with any other status shows the "Already Registered" banner instead. If a later Auto-fill finds no match, the banner disappears. When the lookup is answered from the saved 90-day cache, the match saved with that earlier result is what the form shows.

## 10
When a commit is made, the gate looks at the files staged in that commit and blocks it unless each one was part of a recorded passing test run with exactly the same content (a deleted file counts if it was recorded as missing). It skips Markdown and text files (.md, .mdx, .txt, .rst), anything under the top-level docs/, .memory/, .agents/, .claude/ and .github/ folders, LICENSE files, .gitignore, .gitattributes, common image files (png, jpg, jpeg, gif, svg, webp, ico), and symlinks and submodules. The check only runs where the pre-commit hook is installed, and the record proves tests passed on that content, not that they cover it.

## 11
It flags removed test assertions when, across all changed test files compared with the point where the branch left the default branch, more assertion-like lines were removed than added. Test files are those in tests/test/spec folders or named like test_*, *_test.*, *.test.* or *.spec.*, and an assertion line is one containing words like assert or expect( and similar. Assertions added in another test file offset removals elsewhere, and a changed assertion (one line removed, one added) nets to zero. When it fires it lists each test file that lost more assertion lines than it gained, unless a "tests-removed" exception row for that file path is already merged into the default branch's ARCHITECTURE.md.

## 12
It flags a coverage minimum that is lowered or removed, or a warning limit that is raised or removed, but only in specific files: pytest.ini, pyproject.toml, setup.cfg, tox.ini, .coveragerc, package.json and CI workflow files for fail_under and --cov-fail-under; vitest or jest config files and package.json for lines, branches, functions and statements; and codecov files for target (lowered) and threshold (raised). Limits written as --max-warnings or maxWarnings are checked in those same config and workflow files, not elsewhere. It only fires when an old value was removed in the change, so adding a brand-new limit is not flagged, and tightening is silent. A "threshold" exception row merged into the default branch's ARCHITECTURE.md for the file allows it.

## 13
Yes, but the check is "version changed", not "version higher". For each shipped Markdown document that existed at the comparison point (the point where the branch left the default branch, otherwise the last release tag), the validator errors if the content fingerprint differs and the version number is exactly the same as before. A different version number passes, even a lower one, and a brand-new document is not compared. A separate check on pull requests also requires the overall plugin version to be above the last release's when shipped content changed.

## 14
It depends on which date line. The content fingerprint covers the whole file (after normalising line endings) except frontmatter lines whose key is exactly "version" or "timestamp", so editing only a "timestamp:" line does not count as a content change. A date in the newer "generated: at:" block, or any other date elsewhere in the frontmatter or the body, does count and would require a new version number.
