## 1
When a job is saved, it gets a quality score out of 100 (zero if the title is 2 characters or shorter or the apply link is not a valid web address). It goes live only if the score is 85 or more and none of these problems is present: link known to be unreachable, foreign location, open/talent-pool application, company-portal fallback link, or unverified category. It is archived straight away when a foreign location is its top problem (an unreachable link outranks it and makes it a draft instead), every other case stays a draft, and one override beats all of this: if a job with the same apply link is already live, the save keeps it live. Later, a live job is archived when it is missing from two scans of its company in a row (counted only when that scan found at least one job), or when the link check finds a 404/410, a "position filled" page, a second error in a row, or a posting older than 180 days.

## 2
A job gets those 10 points unless its link is explicitly marked as not answering; a link nobody has checked still gets them. The job also needs a title longer than 2 characters and a valid web address as its apply link, otherwise its whole score is zero. In the code I read, no job connector marks a link as not answering (three of them mark it as answering), so in practice every job with a valid link gets the 10 points.

## 3
The department counts one third as much as the title: a strong keyword is worth 15 points in the title but 5 in the department, a medium one 7.5 versus 2.5, and a weak one 3.75 versus 1.25. The department only adds points for a keyword level the title did not already match. A "wrong field" keyword costs the same 15 points whether it appears in the title or the department. Some job boards (for example Ashby, Personio, Recruitee, Workable, Join and the AI reader) pass a department in; others (for example Greenhouse, Teamtailor, HiBob) send the title alone, so the department plays no part there.

## 4
Each job board connector first reads the board's own field when it has one (for example Ashby's workplace and employment type, Personio's seniority, Recruitee's remote flag, or what the AI reader extracted), and otherwise looks for keywords in the job title such as "remote", "Werkstudent" or "Senior". Seniority comes from the title for most boards; only some boards supply their own seniority or experience value. If nothing is found, the saved job falls back to hybrid, full-time and "experienced". A few connectors (Deel, HeavenHR, Teamtailor) apply those defaults themselves before scoring.

## 5
When the AI job reader gets a quota error (or a reply mentioning "quota"), it stops trying the other AI models for that company and sets a 60-second pause, fixed in the code rather than taken from the provider. That pause only applies to that one reader, and the nightly run creates a fresh reader for every company, so the next company is not paused at all. The error is also swallowed as "no jobs found", so it does not trigger the run's stop-on-quota safety switch. What does carry over within the run is that each key that hit the limit sits out for 60 seconds in the shared key pool.

## 6
The pool picks a key on every call, not only after an error: it takes the least-used key that is not cooling down (ties go to the one used longest ago). If a key returns a rate-limit (429 / "resource exhausted") error, that key sits out for 60 seconds and the same request retries on another key, up to 3 tries (4 when a paid reserve key is set, never more than the number of keys). Other errors, such as a timeout, do not switch keys; the request just fails. If every key is cooling down and no reserve key can be used, it takes the free key whose cooldown ends soonest.

## 7
The paid key is chosen only when, at the moment a key is picked, all five free keys are sitting out their 60-second cooldown after rate-limit errors and the paid key is not itself cooling down. One request makes at most 4 tries, so a request that starts with all five free keys fresh would try 4 free keys and then give up without reaching the paid key. As a last resort within one request, it also falls to the paid key when the pick lands on a key it already tried and no untried free key is out of cooldown. Note that the nightly GitHub job passes in only the main Gemini key setting and no reserve-key setting, so no paid key is configured there.

## 8
The search ignores upper/lower case and looks for the typed text anywhere inside the company's name, its tags, its city or its sector name, so "solar" would also match a name like "SolarX" (illustrative). Commas split the input into separate terms and a company matches if any term is found; spaces do not split, so "solar berlin" is searched as one phrase. The company description is not searched. A match must also pass any other filters you have selected (sector, team size, funding, hiring now).

## 9
The banner appears after you enter a website and click "AI Auto-fill", the lookup succeeds, and the first company in the database whose website contains that domain has the status "draft". If the matching company has any other status, you see the "Already Registered" warning instead. If no company matches, the lookup fails or takes over 3 seconds, or the request is rate-limited or fails, no banner appears. Exception: if that domain was looked up within the last 90 days, the saved result is reused without a fresh database check, so the banner reflects what was found back then.

## 10
Once the hook is installed, it checks every file staged for the commit (compared with the last commit) and blocks the commit if a file's staged content was not part of a recorded passing test run; deleted files count too. It skips documentation and framework files: files ending in .md, .mdx, .txt or .rst; anything under the top-level docs/, .memory/, .agents/, .claude/ or .github/ folders; LICENSE files, .gitignore and .gitattributes; images (png, jpg, jpeg, gif, svg, webp, ico); and symlinks and submodules. Unstaged changes are not checked.

## 11
It compares your branch (including committed, staged, unstaged and new files) with where it split from the main branch, and counts the lines in test files that contain an assertion word such as assert, expect, toThrow or raises. It flags only when, across all test files together, more assertion lines were removed than added; it then names each test file that lost more than it gained. Moving assertions from one test file to another with no net loss is not flagged. The finding is skipped for files covered by a "tests-removed" exception row already merged on the main branch; adding such a row on your own branch is itself flagged.

## 12
It flags a change only when an existing setting line is edited or removed and the new value is looser: a lower coverage minimum (fail_under, --cov-fail-under, lines/branches/functions/statements, Codecov target) or a higher maximum (Codecov threshold, --max-warnings / maxWarnings). Removing the setting with no replacement also counts; raising a minimum, lowering a maximum, or adding a brand-new setting is silent. It only looks in specific files: Python config files, package.json, GitHub workflow files, Jest/Vitest config and Codecov config, and max-warnings only in the Python config files, package.json and workflow files, so a change in an ESLint config file would not be caught. A "threshold" exception row merged on the main branch exempts matching files.

The version must be in x.y.z form. "Before" means the point where your branch split from the main branch (falling back to the last release tag), and documents that did not exist then are not checked. A separate pull-request check does require the overall plugin version to be higher than the last release when shipped content changed.

## 14
It depends on which date line. A "timestamp:" line in the document's header is ignored, together with the "version:" line, so editing only that date is not a content change. A date stored as "at:" under "generated:" in the header (used by several shipped templates) is not ignored, so editing it counts as a content change and needs a new version, as does any date in the document body.
